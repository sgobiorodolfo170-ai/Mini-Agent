## 六、安全说明（规范 §4 / §14）

### Mandate 计算过程

```
子 Run 有效权限 = 父有效权限 ∩ 子 Mandate ∩ 应用策略
```

具体规则：

- `allowedTools`：双方都有取**交集**；只有父有则用父；只有子有则用子
- `deniedTools`：取**并集**（拒绝优先于允许）
- `permissionMode`：取**更严格**一方（`default` < `autonomous` < `full`）
- `authorizedDirs`：子目录必须是父目录的**子集**
- `limits.maxSteps/maxTokens`：取**更小**值
- `canDelegate`：子只有在父也允许时才为 true

### 强制校验入口

`electron/main/agent/index.js` 的 `execute()` 是唯一工具执行入口（子 Agent 复用同一 `execute`），在 `tool.handler` 调用**之前**执行 `authorizeToolCall`。拒绝时：

1. 发出 `mandate.denied` 事件（含 runId/traceId/tool/reason）
2. 写 `agent_tool_calls` 审计（`confirmedBy: 'mandate:<reason>'`）
3. 抛错，工具函数**未被调用**

`tool.before` Hook 仍在 `decide()` 中触发，但仅作为「通知/记录/追加拦截」，**不是安全边界**（符合 §4.4）。

### 路径校验范围

`pathAllowed` 覆盖：

- 路径穿越（`..`）
- 相似前缀（`C:\proj-evil` 不匹配 `C:\proj`）
- 盘符/分隔符大小写（Windows）
- UNC 路径（`\\server\share` 不落入盘符目录）

**未覆盖**：符号链接/目录联接的真实解析。当前实现是静态路径规范化，对已存在的 symlink 不解析真实目标。这是已知缺口，见第九节。

### 尚未覆盖的工具类别

- `mcp_call_tool`：只校验工具名，未校验具体 MCP 工具与参数（MCP 内部工具动态发现，无法静态白名单）
- `browser_*`：只校验 URL 协议，未做域名白名单
- `run_command`：**无参数级校验能力**，按 §4.3 要求归入「需显式授权」

## 七、状态机说明

### Run 状态

```
queued ──► running ──► waiting_child ──► running（子任务返回后恢复）
  │           │
  │           ├──► done / error / max_steps / stopped
  │           └──► transferred（移交，终态）
  └──► stopped / error
```

**终态**：`done`、`stopped`、`error`、`max_steps`、`transferred`
**非终态**：`queued`、`running`、`waiting_child`

约束：
- 终态不可转为任何状态（含自身）
- `waiting_child` 只能回到 `running` 或转 `stopped`/`error`
- 重试必须创建新 Run，不得原地重启

### 验收状态（字段已建，流程待 P1-A）

`not_required`（默认）、`pending`、`accepted`、`rejected`、`escalated`

当前实现：有 `acceptancePolicy` 时，Run 结束置为 `pending`；**验收流程本身未实现**。

### 已知风险

1. **符号链接未解析**：`pathAllowed` 用静态规范化，对已存在的 symlink/junction 不解析真实目标。恶意构造的 junction 可能绕过目录限制。缓解：`run_command` 需显式授权，且 `mandate` 默认不含它。
2. **MCP / 浏览器工具校验粒度粗**：只有工具名白名单，无参数级。规范 §4.3 要求「不能仅凭工具名白名单就判定安全」，当前是**部分符合**。
3. **`updateRun` 兼容层的语义松动**：旧调用方传入非法状态时，现在只打 `console.error` 不抛错，可能掩盖问题。建议 P1 清理所有旧调用点后移除兼容层。
4. **`waiting_child` 未真正等待**：当前只做状态标记，父 Run 的实际挂起/恢复逻辑未接入 Agent Loop（P0-B 只做了状态与关系，恢复由 `session_wait` 轮询驱动）。这是与 §2.2 生命周期描述的**部分实现**。
5. **未验证 `transferred` 的实际执行路径**：事务语义与状态机已验证，但「父 Run 不再恢复、子 Run 接管」的端到端行为依赖上层调用方遵守，未做强制。

## 十二、P0-A 补完（旧流隔离与召回留痕）

### 12.1 旧流隔离（§5.3）

改动位置：`electron/main/agent/index.js`

新增两个闭包内判定：

```js
// Run 仍是本进程内当前活动的那一个，且未被停止
const isCurrentRun = () => {
  if (state.stopped) return false
  const cur = active.get(runId)
  return !!cur && cur === state
}
```

三个拦截点：

| 位置 | 行为 |
|---|---|
| `onDelta` 回调 | 非当前 Run 的增量**不广播**，记 `stale_event_ignored`（kind=delta） |
| `execute()` 工具入口 | 非当前 Run 时**在授权校验与 handler 之前**抛错，杜绝旧流产生真实副作用 |
| Run 结束写库 | `updateRunStatus` 的 CAS + 终态保护拒绝覆盖，并发起 `run.stale_update_ignored` |

审计事件每条 Run 只发一次（`staleNoted` 去重），避免刷屏；原因区分 `stopped` 与 `replaced`。

### 12.2 内部召回留痕（§5.4）

改动位置：`electron/main/gateway/index.js`

`abortStreamsOf` 由静默中止改为返回被召回列表并广播审计：

```js
function abortStreamsOf(conversationId, by = 'unknown') {
  // ...中止并收集
  if (recalled.length) {
    broadcast('stream.recalled', { conversationId, by, msgIds: recalled })
  }
  return recalled
}
```
