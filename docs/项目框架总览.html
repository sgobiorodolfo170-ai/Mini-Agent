01

进程与分层

四个窗口 = 四个渲染入口，共用一份 157 行的 preload。preload 在沙箱内按启动参数 --bridge 只暴露该窗口需要的那一小片 API，主进程再按命名空间分派到 网关 / Agent / RAG / 事件 / 存储 / 系统六个子系统。

02

四个窗口，一份桥

preload 被打包成单入口，靠 additionalArguments 传 --bridge=main|quick|ball|capture 决定暴露哪一组 API。 这不只是省文件数：沙箱 preload 禁止加载相对路径的 chunk，早先的多入口产物会让 window.api 整个消失。

设计取舍

为什么全部用 handle

渲染层没有 send 通道，只有 invoke。 主进程的每次回复都带 Promise 结果或异常，前端能直接 try/catch，不必自己拼回调 id。 需要持续输出的流式回复不用这个方向——它是主进程通过 chat:event 反复推给渲染层的。

两个方向的通道

↓ 请求：inv 先做一次 JSON.parse(JSON.stringify()) 深拷贝。这是给 Vue 的响应式 Proxy 用的—— Proxy 过不了 contextBridge 的结构化克隆，不剥掉会导致调用在序列化阶段静默失败。

↑ 推送：on(channel, cb) 返回取消函数， 视图卸载时调用即可解绑，不需要维护全局监听表。

15 个广播频道

chat:eventchat:attachmentagent:event agent:confirmagent:confirmCancelagent:confirmTimeout kb:progressmodels:progresskeys:event projects:changeddata:changedapp:notice app:routehotkeys:reportstream.recalled

另有 quick:activated 与 quick:selection 只发给快速面板，走 windows.sendTo 定向发送。

五个可观测阶段hooks.js

session.send · run.start · run.end · tool.before · tool.after

三个动作：notify 推通知、log 记事件、block 拒绝。block 只能把允许改成拒绝， 没法把需要确认的写操作放行，所以钩子不会成为绕过确认的通道。 钩子只来自用户写入的设置项，模型无法自行注册。

13 类领域事件hub.js · 500 条环形

run.start / end · tool.before / after · session.created / send / sent · mandate.denied · hook.fired · run.abort_requested · run.empty_result · run.stale_update_ignored · stale_event_ignored

事件只在内存里留存，不落库——写库会拖慢流式路径。每条带单调递增 seq， 前端断线后用 events:since(seq) 增量补拉，不必猜。

Run 状态机 · 只许前进

queued → running · stopped · error
running → waiting_child · done · stopped · error · max_steps · transferred
waiting_child → running · stopped · error

终态五个（done / stopped / error / max_steps / transferred）一律不可再转。 每条 UPDATE 都带 version 与 status 双重条件， 并发写只会有一次成功；被拒的写入打到 stderr 留痕，不静默丢弃。

密钥落盘

优先走 safeStorage 异步接口（Windows 上即 DPAPI）， 其次退到已弃用的同步接口，最后才落到带标记的 base64 明文—— 三种格式互相可区分，不会把明文当密文解。渲染层永远只见末四位。

踩过的坑：Electron 45 的 decryptStringAsync 返回 {shouldReEncrypt, result} 包装对象，直接当字符串用会让鉴权头变成 Bearer [object Object]。解密结果必须归一化。

备份

exporter.js 按固定表序导出（先子表后父表，避免外键顺序问题）， 导入侧做全量替换。加密函数由调用方注入，所以在 vitest 里也能跑。
