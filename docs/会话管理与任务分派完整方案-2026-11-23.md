# 会话管理与任务分派完整方案

2026-11-23

保留方案四对会话和任务的区分。会话保存对话和呈现历史，`agent_runs` 记录一次具体执行。所有 Agent 任务通过同一个运行服务创建、排队、取消和读取结果。父 Agent 通过三个明确的动作控制流程：派发后继续，等待时暂停，移交成功后退出。

本方案首版已接入生产代码。首版包含有界并发、同会话互斥、事务移交、取消、排队恢复与启动收口；自动验收、通用依赖图、运行中断点续跑与独立工作区留作后续扩展，首版的成功状态只表示执行产生有效结果。实施状态见 §7。

## 1. 现状与选型

接入前，`session_send` 创建子 Run 时直接更新父 Run 的状态，但 Agent 循环只读取内存停止标记。用模拟工具运行现有循环时，父任务在标为 `waiting_child` 和 `transferred` 后都执行了同一批次的后续工具，并进入下一次模型调用。会话查询还可能把最近一次 Agent Run 的状态和最近一条普通聊天回复组合成同一个结果。子 Run、父状态和消息当时分步写入，缺少覆盖完整派发流程的事务。见 [Agent 入口](../electron/main/agent/index.js)、[执行循环](../electron/main/agent/loop.js) 和 [会话实现](../electron/main/agent/sessions.js)。

| 方案                                    | 收益                                                  | 代价                                                                             |
| --------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| 给现有两条链路分别补等待和移交          | 变更面小，适合紧急修补                                | 临时 Agent 与持久 Run 仍有各自的调度、停止和审计语义。会话轮次歧义也需要另行处理 |
| **统一 Run 调度，显式派发、等待、移交** | 保留现有表和界面基础，能统一执行语义并按 Run 跟踪结果 | 需要修改循环控制、迁移数据库，并让桌面与远程入口共享服务                         |
| 引入通用工作流引擎                      | 适合预声明依赖图和持久执行检查点                      | 需要持久化模型上下文、工具副作用和补偿策略，当前桌面任务场景难以承担这部分复杂度 |

采用第二项。首版包含有界并发、同会话互斥、事务移交、取消及排队恢复。已开始执行的任务在重启后以中断结束。自动验收、通用依赖图、运行中断点续跑与独立工作区留作后续扩展，首版的成功状态只表示执行产生有效结果。

## 2. 接口与兼容

公开工具名为设计契约。底层服务应由桌面 IPC、远程 API 和模型工具共用。用户级入口按用户、设备及项目访问策略授权，模型级入口使用运行服务注入的 `callerRunId`，模型参数不能指定调用者身份。

| 接口                        | 输入                                   | 返回与行为                                                                                                             |
| --------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `run_dispatch`              | `goal`，可选 `conversationId`、`title` | 返回 `{ runId, conversationId, status, reused }`。缺目标会话时创建子会话。提交后父 Run 继续                            |
| `run_wait`                  | `runIds`、可选 `timeoutMs`             | 返回 `{ timedOut, runs }`。只等本次指定的直接委派子 Run。等待时间默认 60 秒，上限 300 秒。超时返回当前快照，子任务继续 |
| `run_transfer`              | `goal`，可选 `conversationId`、`title` | 返回接手 Run 信息，同时由执行器向循环发出内部 `exit` 控制结果。要求父 Run 没有活动的委派子 Run                         |
| `run_status` / `run_result` | `runId`，结果可带裁剪上限              | 按 Run 返回状态或该 Run 的交付文本、摘要与截断标记。交付文本为终态结果，运行中的进度从状态和事件获取                   |
| `run_cancel`                | `runId`                                | 返回当前状态和是否已提交取消请求。工具只能取消自己派发的直接子 Run，用户级入口按现有授权控制                           |

`run_wait` 去重并保持输入顺序，拒绝空列表、自身及非直属委派子 Run。它返回每个 Run 的状态以及已完成项的结果，包括失败、取消和中断原因。若直属委派子 Run 已移交，父任务等待同一条移交链的最终接手方，并返回最初委派的子 Run 与接手方 ID。该解析权限仅用于调用方自己的委派分支，按派生深度限制追踪。

- `session_create/list/status` 保留会话视角。会话概览以最近一轮对话绑定的执行或消息派生状态。历史任务、混合聊天及结果深链一律使用 `runId`。旧 `session_wait/result` 在调用入口锁定当时的最新轮次标识，等待期间后续消息不会改变查询目标。
- `session_send(mode=chat)` 保留普通聊天。旧 `session_send(mode=agent, delegated)` 转发到 `run_dispatch`，`transferred` 转发到 `run_transfer`，返回原接口已有的消息及 Run 标识，并遵守新的执行控制。模型工具描述同步更新。`acceptanceCriteria` 可保留为用户验收提示，界面明确区分执行完成与人工验收。旧验收字段可读。
- `spawn_agent` 保留一次调用返回汇总的体验，内部使用批量派发加等待。默认每个目标新建一个子会话，按目标顺序汇总。单项失败返回该项错误。等待超时时带回未完成的 Run ID，方便后续查询。批量登记全成或全退，防止部分提交后重试重复派发。
- 同会话默认只有一个活动写入者。Agent 派发到显式指定的会话遇到活动聊天或 Run 时返回 `SESSION_BUSY`。普通聊天保留主动替换同类聊天的行为，沿用流所有者检查，禁止替换活动 Agent；重生成、编辑重发和删除也经同一仲裁入口。派发到父会话自身返回 `INVALID_TARGET`，通过新建或复用空闲子会话运行。

## 3. 数据与状态

以当前 `SCHEMA_VERSION = 9` 为基线（v8→v9 增加运行队列、消息关联、移交与恢复字段）。保留 `agent_runs.parent_run_id`、`control_mode`、`trace_id` 和 Mandate。`control_mode` 表示边的类型，即当前 Run 如何从父 Run 派生。运行是否已交出控制权由自身状态和接手 Run 决定。

| 存储                            | 字段与约束                                                                                                                                                                                                                                                         |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `agent_runs`                    | 增加 `submitted_at`、`claimed_at`、`finished_reason`、`user_message_id`、`assistant_message_id`、`transfer_to_run_id`、`run_spec_json`。`run_spec_json` 持久化可恢复执行的必要参数，包括版本、模型配置标识、上下文边界及预算。禁止写入密钥。旧记录新增字段允许为空 |
| `run_dispatch_requests`         | 以 `(principal_scope, request_key)` 唯一标识请求。保存规范化内容摘要和结果引用。同键同内容返回原记录，同键异内容返回 `IDEMPOTENCY_CONFLICT`。模型工具键由执行器基于父 Run 与持久化的工具调用身份构造，桌面和远程入口使用各自请求身份                               |
| `run_events` 或既有持久事件设施 | 复用能在业务事务里写入、支持递增游标的持久事件设施。提交后通知进程内订阅者和 IPC。事件载荷包含标识、状态、原因及版本，文本通过结果接口读取                                                                                                                         |

任务消息通过 Run 上的消息 ID 精确关联。新 Run 的用户提示和助手占位在登记时同事务写入，占位采用 `pending`。领取后改为 `streaming`，收口时与 Run 一起写入终态和结果。聊天入口独立管理聊天状态，并共享会话互斥。

| Run 状态                                                              | 允许的后续状态                                                                         | 说明                                                                             |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `queued`                                                              | `running`、`stopped`、`error`                                                          | 已登记且未被执行器领取，占用目标会话。配置失效可在领取前收口为 `error`           |
| `running`                                                             | `waiting_child`、`transferred`、`done`、`error`、`max_steps`、`stopped`、`interrupted` | 当前循环可推进。只有等待动作进入 `waiting_child`，只有事务移交进入 `transferred` |
| `waiting_child`                                                       | `running`、`error`、`stopped`、`interrupted`                                           | 父循环停在同一个等待调用。条件满足或超时后恢复，取消与进程中断直接收口           |
| `done`、`error`、`max_steps`、`stopped`、`interrupted`、`transferred` | 无                                                                                     | 终态及其原因保持稳定。`transferred` 的最终任务结果沿 `transfer_to_run_id` 查询   |

以 `version` 和源状态做条件更新。停止请求属于控制状态，复用桌面和远程现有控制接口。运行中先记录停止请求并阻止启动新动作，执行器确认退出后才释放会话。已经进入外部工具的调用依工具能力中止，结果不明时在终态原因中明确记录。结构化结果区分成功、失败、步数耗尽、用户停止、进程中断和移交。

## 4. 提交、调度和运行控制

**创建或移交。** 在 Electron 主进程通过同步 SQLite 写事务校验请求身份、幂等、父状态、深度、授权和会话占用。写入子会话（如需）、`queued` Run、消息和事件。移交额外写入父 Run 的 `transferred` 状态、`transfer_to_run_id`、结束时间和对应消息。任一写入失败整体回滚。提交之后才发通知和启动调度。活动 Agent 在会话上有唯一约束，聊天流登记与事务在同一主进程仲裁器串行完成。

**领取。** 调度器按提交时间和 ID 领取最早满足约束的任务，跳过资源暂时不可用的队首。领取事务将 `queued` 改为 `running` 并记录 `claimed_at`。领取成功后才发起模型或工具调用。配置和授权变化时退出或收紧权限。模型 Key 由现有网关选择，队列调度与 Key 轮换各自负责自己的资源。

**执行。** `runAgentLoop` 在模型请求前、每条工具执行前和工具返回后处理停止、暂停及移交信号。控制结果独立于工具返回的模型文本。移交成功立即结束父循环并跳过同批剩余工具，父消息和事件统一呈现 `transferred`。等待期间不请求模型或执行后续工具。等待服务先读取快照，再订阅后重读，收到事件时按数据库重算条件。有界轮询兜底，完成、取消或超时均解绑订阅。

**并发与预算。** 首版默认全局最多 4 个活动执行槽，集群开启时每个父 Run 最多 2 个活动委派子 Run，关闭时为 1。活动子 Run 上限计入 `queued`、`running` 和 `waiting_child`，移交链按同一个委派分支计数。单批最多 2 项，超过上限明确拒绝。派生深度为 2，移交也计入深度。等待和已确认暂停的父 Run 释放执行槽并保留会话占用，恢复前重新竞争槽。`spawn_agent` 内置等待也走这一流程，避免低并发配置下父任务占满槽而子任务无法启动。任何 Run 都必须遵守自身和继承得到的最大步数，以及明确配置的共享链路预算。可预留预算时在调用前原子扣留，结束后按实际使用结算。首版使用现有步数限制和活动子任务上限，令牌总预算需要服务端用量可观测后再开启。

**结果与停止。** 终态、助手文本及终态事件同事务提交，提交后再唤醒父等待。父任务取消时递归取消仍归它的委派子任务，并沿这些分支追到当前接手方。移交已经提交的父 Run 保持 `transferred`，直接取消接手 Run 需获得接手方的访问权限。取消先于移交提交时移交失败，移交先提交时返回接手方，不覆盖父终态。父任务自然结束时，剩余委派任务按同样的取消规则收口。所有等待均可被树取消和应用退出打断。

## 5. 权限、上下文和重启

**权限。** 派发、读取、等待和取消统一校验目标归属。子任务授权为父有效 Mandate、子任务请求范围和应用策略的交集。目标模型或项目的变更不能扩大授权范围。工具执行仍使用现有强制校验，领取时重新检查父授权快照及当前策略。全局幂等查询不得绕过主体与目标权限校验。高风险工具沿用现有审批，审批与授权按 Run 隔离。

**上下文。** 新子会话从明确的目标和必要的交接摘要开始，使用创建时确定的模型配置与上下文边界。复用子会话时只能读取该会话在派发前可见的历史及本次输入。移交摘要包含剩余目标、已有交付、未决事项和有权访问的引用。工具日志、密钥和无关会话历史不会随任务复制。结果接口使用现有输出裁剪机制。

**应用退出与恢复。** 退出时停止接单和领取，唤醒等待并中止正在执行的任务。已登记、尚未领取的根任务及承接根任务的 Run 留在队列，待下次启动调度。已终止父 Run 的委派分支随父任务收口，包括分支中已接手的 Run。启动时按如下规则一次性校正 Run、消息及审批，然后启动调度器。

| 启动时记录                           | 恢复动作                                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `queued` 且有完整 `run_spec_json`    | 有效授权和依赖校验后重新入队。原派发标识保持稳定。所属父任务中断的普通委派分支收口为 `stopped`   |
| `running` / `waiting_child`          | 标记为 `interrupted`，更新关联消息，取消未决审批。保留审计及已经持久化的内容。用户重试创建新 Run |
| `transferred` 且接手 Run 仍 `queued` | 保留移交终态。接手方若承接根任务则恢复排队，若仍属于已终止父任务的委派分支则收口为 `stopped`     |
| 接手 Run 已领取但未提交终态          | 接手 Run 标记为 `interrupted`。移交链保留，用户从接手方重试                                      |
| 旧版无运行规格的活动记录             | 保守收口并记录 `legacy_unrecoverable`。历史终态继续可读                                          |

领取事务和首次外部调用之间崩溃时，也按已领取中断处理。这可能要求用户重试一次尚未产生副作用的运行，避免误重放可能已经执行的外部动作。重启逻辑应替换当前数据库打开时对所有 `streaming` 消息的统一处理，再单独保留普通聊天流的旧恢复语义。见 [数据库启动逻辑](../electron/store/db.js)。

## 6. 迁移、实施顺序和发布验收

1. **存储与兼容。** 添加列、索引和事件写入接口。以既有消息 `meta` 中可唯一确认的 Run 引用回填消息 ID，歧义记录保留为空。用唯一 `control_mode=transferred` 的父子边回填接手关系，有歧义的记录继续作为历史显示。迁移事务内收口旧活动记录，再建活动会话唯一索引。备份升级前数据库并验证恢复过程，旧版应用回退配合升级前备份。
2. **贯通父子链路。** 接入派发、单槽调度、显式等待、事务移交和一致终态。桌面、远程和模型入口共用运行服务。通过正常入口的模拟模型测试验证工具批次、消息及事件行为。
3. **接入并发、取消和恢复。** 开启父级与全局配额，迁移 `spawn_agent`，串接现有桌面和远程的暂停、终止与审批。桌面子会话看板与移动端根据 Run 状态和移交链接显示实时进度。
4. **释放新路径。** 同一安装实例内所有 Agent 启动入口统一切到新执行服务。保留旧工具和 IPC 的适配层以读取历史并过渡现有调用；兼容层走同一套状态机。验证通过后再考虑移除旧入参别名。

| 验收场景                                       | 应观察到的结果                                                                           |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 用现有版本数据库升级                           | 会话或 Run ID 保持稳定。历史结果可读，混合聊天和 Agent 任务的新版结果按 Run 精确定位     |
| 普通派发后继续工作，再等待两个子任务           | 父任务派发时仍在运行。等待时不调用模型或工具，等齐后只恢复一次，按输入顺序返回成功与失败 |
| 模拟模型在一批工具中先移交再请求有副作用的操作 | 移交成功后后续工具和模型调用次数均为零。父消息、数据库及事件状态一致                     |
| 在事务各次写入后分别注入失败                   | 父状态、消息、关系、事件和请求记录全部回滚。按同一请求键可安全重试                       |
| 相同请求重复提交及同会话并行提交               | 同键同内容返回同一 Run，同键异内容报冲突。同会话最多有一个活动写入者                     |
| 把全局执行槽设为 1，再派发并等待               | 父任务释放槽后子任务可运行，父任务随后恢复，无死锁                                       |
| 模拟快任务、等待超时、停止与移交竞争           | 快任务不会丢唤醒，超时返回快照，停止树无残留等待。移交和取消按提交先后得到唯一结果       |
| 应用在事务提交前、提交后未领取、领取后分别退出 | 分别得到完整回滚、重新入队、明确中断。无重复领取和外部工具重放                           |
| 通过模型、桌面、远程分别请求访问无权 Run       | 无法读取状态或结果、投递或取消。子权限受父授权和当前策略约束                             |
| 使用旧会话工具与 `spawn_agent`                 | 普通聊天、结果汇总和会话历史继续可用，任务关系与实际执行状态可在同一视图追踪             |

现有 6 个相关单测文件的 62 项用例通过。第一轮内存原型验证了显式等待下的多子任务收口，以及移交事务回滚和退出信号。首版接入后，`agent-dispatch-flow`、`agent-run-queue`、`lifecycle` 与 `agent-run-relations` 覆盖了批次内移交后跳过剩余工具、等待收口、队列领取与重启收口；跨重启和多入口行为仍以本节验收场景为准。

## 7. 实施状态（2026-11-24）

首版运行服务已落地，桌面、远程和模型工具共用同一套 Run 状态机。

| 能力 | 状态 | 落点 |
| --- | --- | --- |
| 统一登记、幂等与事务 | ✅ | `electron/main/agent/index.js` `registerRuns`、`run_dispatch_requests` |
| 有界并发与同会话互斥 | ✅ | `electron/main/agent/run-runtime.js` `createRunQueue`（全局 4 槽，父级集群 2 / 普通 1） |
